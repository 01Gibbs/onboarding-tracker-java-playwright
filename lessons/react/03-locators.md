# Lesson 03: Locators

**Goal:** find elements robustly, the way a user would, and work with lists and tables, including the
moments when a React page is still catching up.

**Time:** about 1.5 hours

**Docs:** [Locators](https://playwright.dev/docs/locators) · [Other locators](https://playwright.dev/docs/other-locators)

## Concepts

### Which locator, in order of preference

| Locator | Example | Use when |
|---------|---------|----------|
| `getByRole` | `getByRole('button', { name: 'Search' })` | Almost always. It matches what users and assistive tech see |
| `getByLabel` | `getByLabel('Email')` | Form fields |
| `getByPlaceholder` | `getByPlaceholder('Name or email')` | Inputs without a label (rare) |
| `getByText` | `getByText('No customers match your search.')` | Non-interactive text |
| `getByTestId` | `getByTestId('account-balance')` | When there's no good user-facing handle |
| `locator('css')` | `locator('#movement-form')` | Last resort. Ask whether the page is missing an accessible name instead |

Text matching is **case-insensitive and substring** by default. Pass `{ exact: true }` for an exact match.

React components don't change this: a `<button>` rendered by React is still a button with a name. Avoid
locators tied to how the app is built (class names generated by CSS-in-JS, component names): they change
when the code does, while roles and labels change only when the product does.

### Strictness

Actions such as `click()` and `fill()` need the locator to match **exactly one** element. If it matches more,
Playwright throws a *strict mode violation* that lists the matches. That's a feature: it stops you clicking the
wrong thing. Fix it by narrowing the locator.

### Narrowing: chaining and filtering

```ts
const mainNav = page.getByRole('navigation', { name: 'Main' })
await mainNav.getByRole('link', { name: 'Customers' }).click()

const table = page.getByRole('table', { name: 'Customers' })
const row = table.getByRole('row').filter({ hasText: 'Dan Evans' })
await expect(row.getByTestId('status-badge')).toHaveText('Suspended')
```

`filter` also takes `has: otherLocator`, `hasNot`, and `hasNotText`. Lists: `first()`, `last()`, `nth(i)`,
`all()`, `count()`, and `await expect(list).toHaveCount(n)`.

> Locators are **lazy**. Creating one does nothing; it's looked up fresh every time you act or assert, so you
> can define one early and reuse it after the page changes.

### Lists that are still loading

A React page shows its frame first and fills it in when the API answers. After you click "Search", the
**old** rows stay on screen until the new ones arrive. Two consequences:

- `toHaveCount`, `toHaveText` and friends retry, so they wait for the new rows. Good.
- `await rows.all()` takes a **snapshot**, right now. Loop over it and you may be checking the old rows.

So to check every row, describe the rows that would be wrong, and expect there to be none:

```ts
await expect(rows.filter({ hasNot: page.getByText('Frozen', { exact: true }) })).toHaveCount(0)
```

"None" is also true of an empty table, such as a list that is still loading. So check it again once a row you
expect is on screen.

### Finding a locator interactively

Run `npm run test:react -- --ui`, or put `await page.pause()` in a test and run it `--headed`. "Pick locator"
suggests a locator for whatever you click.

## Exercise

Open the starter `e2e-react/lesson03/locators.spec.ts`. The `beforeEach` sign-in is provided, and each test
is just a name. Its goal is below.

1. **Navigation.** Click "Customers" *inside the Main navigation*, and expect the "Customers" heading to be
   visible. Then expect the nav link to have `aria-current="page"`.
   *Try `page.getByRole('link', { name: 'Customers' }).click()` from the dashboard first, and read the
   error. What else matches?*
2. **Search.** On `/customers`, fill the field with the placeholder "Name or email" with `archer` and click
   "Search". Expect exactly 1 `customer-row`, containing "Alice Archer", and `result-count` to say
   "1 customer".
3. **Table rows.** On `/customers`, find Dan Evans's row **inside the "Customers" table**. Expect its status
   badge to say "Suspended", and its first cell to say "CUS-0004".
4. **Text.** On `/customers`, expect `getByText('alice.archer@')` to be visible (substring match), and `getByText('Erin
   Foster', { exact: true })` too.
5. **Every row.** On `/accounts`, choose Status = Frozen and click "Apply filters". Expect the "Holiday Fund"
   row to be visible, and **no** row to have a badge other than "Frozen". (Try a loop over `.all()` first, run
   it a few times with `--repeat-each=10`, and see whether it's reliable. On a fast machine it may pass every
   time: the race is real, it just needs a slow moment to show, which is why it fails in CI first.)
6. **`has` filter.** From Alice Archer's customer page, click the account link in the row of the "Accounts"
   table that **has** a cell with exactly the text "Savings". Expect the h1 to contain "Rainy Day" and the
   account number to be `10000002`.

## Discussion

- Why does `getByRole` beat a CSS selector like `.topbar nav ul li:nth-child(2) a`?
- In exercise 5, why not `await expect(rows).toHaveCount(1)`? (Hint: other tests may freeze accounts too.)
- In exercise 5, what exactly can go wrong with the loop, and why would it only go wrong *sometimes*?
